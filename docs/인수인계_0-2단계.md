## 담당자가 할 일 (Supabase 대시보드 권한 필요)

### 1. 마이그레이션 적용 (김태현)
`supabase/migrations/`의 새 파일 3개를 **이름 순서대로** 적용합니다. 지금 DB(22개 테이블 + seed.sql) 기준입니다.

| 순서 | 파일 | 내용 |
|---|---|---|
| 1 | `20261026000300_auth_rls.sql` | `auth_user_id` 컬럼, 계정 자동 연결 트리거, RLS 정책 |
| 2 | `20261026000400_sales_forecast_fn.sql` | 매출 예측 함수 `generate_sales_forecast` |
| 3 | `20261026000500_seed_accounts_email.sql` | 시드 계정 login_id → `owner@example.com` 등 이메일 |

- **CLI 사용 시:** `supabase migration list`로 원격 이력을 먼저 확인합니다. init(`20261014000000`)을 SQL Editor로 넣었다면 원격 이력에 없으므로 `supabase migration repair --status applied 20261014000000` 후 `supabase db push`를 실행합니다. (안 하면 init을 다시 실행하려다 "already exists" 오류가 납니다)
- **SQL Editor 사용 시:** 세 파일을 순서대로 하나씩 붙여 넣고 Run합니다. 기존 정책 drop 때문에 "destructive operation" 경고가 뜨면 확인하고 실행합니다.
- 확인: `select login_id, auth_user_id is not null as linked from user_account;` → `login_id`가 이메일이면 성공 (`linked`는 사용자를 만들기 전이라 `false`가 정상)

### 2. 로그인 사용자 만들기
Authentication → Users → **Add user → Create new user**에서 아래 이메일로 만들고 **Auto Confirm User를 켭니다**. 만드는 즉시 DB의 직원 계정(`user_account`)과 자동 연결됩니다.

| 이메일 | 이름 | 역할 | 들어가는 화면 |
|---|---|---|---|
| `owner@example.com` | 김찬영 | 점주 | `#/owner` |
| `jang@example.com` | 장윤서 | 매니저 | `#/manager` |
| `jung@example.com` | 정윤수 | 알바생 | `#/staff` |

- 나머지 알바생(`park`·`lee`·`choi`·`han@example.com`)도 필요하면 같은 방식으로 만듭니다.
- **SQL로 한 번에 만들기(개발용):** `supabase/handoff/create_test_users.local.sql`을 SQL Editor에서 실행하면 7명이 같은 테스트 비밀번호로 만들어지고 자동 연결됩니다. 비밀번호가 들어 있어 git에서 제외된 파일이므로(`*.local.sql`) 저장소에는 없고, 작성자에게 직접 받아야 합니다. 실제 운영 전에는 비밀번호를 바꾸거나 이 사용자들을 지웁니다.
- 비밀번호는 만드는 사람이 정해서 팀에 따로 전달합니다. **저장소·문서에 적지 마세요.**
- `example.com`은 예시 주소라 메일이 가지 않습니다. 그래서 Auto Confirm을 켜야 합니다.
- 확인: SQL Editor에서 `select login_id, auth_user_id is not null as linked from user_account;` → 만든 계정이 `true`

### 3. (권장) 공개 회원가입 끄기
Authentication → Sign In / Providers → **Allow new users to sign up 끄기**.
지금은 켜져 있습니다. 켜 두어도 매장 계정과 연결되지 않은 사용자는 데이터를 볼 수 없지만, 계정은 점주가 만든다는 설계(7-1)에 맞추려면 끄는 편이 좋습니다.

## 무엇이 바뀌었나

### DB ([migrations/20261026000300_auth_rls.sql](../supabase/migrations/20261026000300_auth_rls.sql), [20261026000400_sales_forecast_fn.sql](../supabase/migrations/20261026000400_sales_forecast_fn.sql))
- **테이블 추가 없음** (22개 유지). `user_account`에 `auth_user_id uuid` 컬럼만 추가, `password_hash`는 사용 안 함(nullable).
- 로그인은 Supabase Auth가 담당. `user_account.login_id`에 **로그인 이메일**을 넣어 두면, 같은 이메일의 인증 사용자가 확인되는 순간 트리거가 연결합니다(`초대됨` → `활성`).
- RLS: 로그인 안 한 사용자(anon)는 아무것도 읽지 못합니다. 모든 접근은 **같은 매장(store_id)** 으로 제한됩니다.

| 역할 | 읽기 | 쓰기 |
|---|---|---|
| 점주 | 매장 데이터 전체 | 매장 데이터 전체 (계정의 `password_hash`·`auth_user_id`는 불가) |
| 매니저 | 매장 데이터 (알림은 본인 것만) | 스케줄 검토(배정 수정·상태 변경), 재고·재고 변동, 입고, 부족 신고 처리 |
| 알바생 | 본인 가능시간·출퇴근·급여, 공개된 스케줄, 재고·부족 신고 (매출 X) | 본인 가능시간·출퇴근, 부족 신고 |

- RLS 헬퍼 함수는 `app` 스키마에 있습니다: `app.my_user_id()`, `app.my_store_id()`, `app.my_role()`, `app.is_owner()`, `app.is_admin()`(점주·매니저) 등. 다음 단계 정책에서 그대로 쓰면 됩니다.
- 예측 함수 `generate_sales_forecast(대상주 월요일, 주 수=4)` (점주만 실행)
  - 예측 = 최근 4주 같은 요일·시간대 평균 × (1 + 증감률), 증감률은 최근 1주 vs 이전 주 평균, ±20% 제한
  - 필요 인원 = 시간당 5만원 미만 1명 · 10만원 미만 2명 · 이상 3명 / 피크 = 3명 시간대 / 증원 검토 = 최근 실적 기준보다 인원이 느는 시간대
  - 같은 주를 다시 계산하면 기존 행을 지우고 새로 넣습니다.

## 체험 로그인 모드 (마이그레이션 적용 전 임시)
- `app/.env.local`에 `VITE_DEMO_LOGIN=true`를 넣거나 Supabase 환경변수가 없으면, Supabase Auth 대신 브라우저 안에서만 확인하는 테스트 계정으로 로그인합니다. 로그인 화면에 "체험 모드" 안내가 보입니다.
- 계정: `owner@example.com`(점주) · `jang@example.com`(매니저) · `jung@example.com`(알바생), 비밀번호 모두 `123456`. 역할별 접근 제한은 실제와 같습니다.
- 매출 화면은 지금 원격 DB가 로그인 없이 읽히는 상태라 실제 데이터로 보입니다. **마이그레이션을 적용하면 이 읽기가 막히므로 `VITE_DEMO_LOGIN` 줄을 지우고 실제 로그인으로 바꿔야 합니다.** Vercel에는 이 변수를 넣지 않습니다.
- ⚠️ **알려진 버그(미해결):** 체험 모드에서 로그아웃한 직후 같은 탭에서 다른 계정으로 로그인하면 들어가지지 않는 경우가 자동 테스트에서 재현됐습니다. 새로고침 후 로그인하면 됩니다. 원인 조사 중에 작업을 멈췄습니다.

## 알아 둘 점
- **SQL 적용 후 루트 `index.html`(초기 단일 파일 프로토타입)은 DB를 읽지 못하고 예시 데이터로만 보입니다.** anon 읽기를 막았기 때문이며 의도된 것입니다. 현재 앱은 `app/`입니다.
- 시드는 매출 집계가 1주치(10.05~10.11)뿐이라 증감률이 0 → 예측값이 그 주 실적과 같게 나옵니다.
- 시드 판매 기록(10.14)이 집계 주 밖이라 "메뉴별 판매"는 비어 보입니다. 1-1 판매 기록 출처(POS 여부)가 정해지면 해결됩니다(미정 — 임의로 정하지 말 것).
- 대시보드의 재고·근무표·알림 카드와 0~2단계 밖의 화면은 아직 예시 데이터입니다.
- 예측 자동 실행(매주)은 15단계(스케줄러)에서 붙입니다. 지금은 점주가 버튼으로 실행합니다.
- 계정 전환 직후 아주 짧게 이전 계정 역할로 판단될 수 있는 여지가 있습니다(실사용 영향은 작음). 7-1 직원 계정 작업 때 같이 정리하면 됩니다.
