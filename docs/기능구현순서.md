# 기능 구현 순서 (인증 포함)

기준: [프로세스 목록 보완본](<../산출물/5주차/프로세스목록보완5조.docx>)의 우선순위(상 → 중 → 하)를 따르되, **앞 단계의 데이터가 있어야 뒤 단계가 돌아가는 의존 관계**를 우선한다. 테이블은 확정된 22개만 쓴다.

## 현재 상태 (2026-10-21)
- 화면 레이아웃(React, 해시 라우팅)은 배포됨. 모든 데이터는 `app/src/mocks/data.js` 예시 값이고 `state/AppState.jsx`가 들고 있다.
- Supabase 연결 완료: `app/src/lib/supabase.js` (`NEXT_PUBLIC_*` 환경변수, 로컬은 `app/.env.local`). DB에는 22개 테이블 + 시드가 들어 있고 RLS는 켜져 있다. 지금 정책은 **anon 읽기 전용**(10개 테이블)이며 쓰기 정책은 없다.
- 화면 교체 방식: 화면 코드는 건드리지 않고 `AppStateProvider` 내부만 mock → Supabase 조회·저장으로 바꾼다.
- **5~7단계(2-4·2-5·2-6) DB 연동 완료**: `lib/scheduleRepo.js`(work_schedule·shift_assignment 저장), `AppState`의 `saveScheduleDraft`·`editScheduleCell`·`changeScheduleState`, 마이그레이션 `20261026000200_schedule_review_publish.sql`(E4 확정 차단·E5 공개 알림 트리거, **임시 anon 쓰기 정책 — 0단계에서 교체**). 사용자 id는 아직 인증이 없어 `mocks/data.js`의 `userId`(seed 기준)로 고정한다.
- **3단계(2-1)·4단계(2-3) 구현**: `supabase/migrations/20261026000100_availability_schedule_rpc.sql`의 DB 함수(`get_availability`, `save_availability`, `get_schedule`, `generate_schedule_draft`)를 `app/src/lib/api.js`로 호출한다. 인증 전이라 사용자는 예시 데이터의 `dbId`로 고정했고(0단계에서 `auth.uid()`로 교체), 다음 주 예측이 없으면 가장 최근 예측 주로 필요 인원을 계산한다(2단계 완료 시 해소).
- 8~10단계 코드 완료(인증·2-1 포함). **원격 DB에는 미적용**이며, 반영 절차는 [8-10단계_DB반영_안내.md](8-10단계_DB반영_안내.md)를 따른다.
- 화면 레이아웃(React, 해시 라우팅)은 배포됨. 0~2단계 외의 데이터는 아직 `app/src/mocks/data.js` 예시 값이고 `state/AppState.jsx`가 들고 있다.
- Supabase 연결: `app/src/lib/supabase.js` (`NEXT_PUBLIC_*` 환경변수, 로컬은 `app/.env.local`). 환경변수가 없으면 앱은 **예시 모드**(로그인 없이 역할 카드, 모든 화면 예시 데이터)로 동작한다.
- **0~2단계 구현 완료** (`feature/auth-sales` 브랜치)
  - 0 인증: Supabase Auth 이메일/비밀번호 로그인·로그아웃·세션 유지, 역할별 라우트 가드 — `app/src/lib/auth.jsx`, `features/auth/EntryPage.jsx`
  - 0 RLS: anon 읽기 제거, 같은 매장(`store_id`)만 + 역할별 쓰기 — `supabase/migrations/20261026000300_auth_rls.sql`
  - 1 매출 현황(1-2): `sales_summary` 최근 주·최근 4주 평균 히트맵, `sale` 메뉴별 판매 — `features/sales/useSales.js`
  - 2 매출 예측(1-3): `sales_forecast` 조회 + 점주가 누르는 "다음 주 예측 계산"(DB 함수 `generate_sales_forecast`) — `supabase/migrations/20261026000400_sales_forecast_fn.sql`
- 화면 교체 방식: 화면 코드는 건드리지 않고 `AppStateProvider` 내부만 mock → Supabase 조회·저장으로 바꾼다. (매출은 `useSales` 훅으로 분리)

### 0~2단계 DB 적용 방법
자세한 절차는 [인수인계_0-2단계.md](인수인계_0-2단계.md)를 본다.
1~2. `supabase/migrations/`의 `20261021*` 마이그레이션 3개 적용 (인증·RLS, 예측 함수, 시드 계정 로그인ID를 `owner@example.com` 등 이메일로 변경)
3. Authentication → Users → Add user에서 같은 이메일로 사용자를 만들고 **Auto Confirm User**를 켠다 → `user_account`에 자동 연결된다
4. Authentication → Sign In / Providers에서 **Allow new users to sign up을 끈다** (계정은 점주가 만든다. 켜 두어도 매장 계정과 연결되지 않은 로그인은 데이터에 접근하지 못한다)

### 역할별 권한 요약 (RLS)
| 역할 | 읽기 | 쓰기 |
|---|---|---|
| 점주 | 매장 데이터 전체 | 매장 데이터 전체 (계정의 `password_hash`·`auth_user_id`는 불가) |
| 매니저 | 매장 데이터 (알림은 본인 것만) | 스케줄 검토(배정 수정·상태 변경), 재고·재고 변동, 입고, 부족 신고 처리 |
| 알바생 | 본인 가능시간·출퇴근·급여, 공개된 스케줄, 재고·부족 신고 | 본인 가능시간·출퇴근, 부족 신고 |

## 먼저 정할 것 (구현 전에 팀 결정)
1. ~~**인증 방식**~~ — Supabase Auth(이메일/비밀번호)로 구현함. `user_account.login_id`에 로그인 이메일을 넣고 `auth_user_id`로 연결, `password_hash`는 사용하지 않음(nullable).
2. **1-1 판매 기록 출처(POS 연동 여부)** — 미정. 정해질 때까지 시드 데이터 + CSV 업로드/수동 입력으로 대체하고, 연동 방식이 확정되면 교체한다.

## 순서의 근거
- **인증이 0단계**인 이유: 모든 쓰기·역할별 화면이 "누가 로그인했는가"에 의존하고, 지금의 anon 읽기 정책은 임시라서 인증 후 바로 좁혀야 한다.
- 상 우선순위의 1위(2-3)는 **예측(1-3)과 가능시간(2-1)이 있어야** 만들 수 있어서 둘을 앞에 둔다. 1-1(상7)이 마지막인 이유는 출처가 미정이고, 시드 데이터로 1·2단계를 먼저 검증할 수 있기 때문이다.
- 기초 정보 등록(하)은 우선순위는 낮지만 재고·발주(12·13단계)의 선행 데이터다. 읽기는 시드로 충분하므로 쓰기(CRUD)를 10단계에 둔다.
- 각 단계는 "화면 연결 → 저장 → 이벤트(자동 반응)" 순으로 끝낸다.

## 작업 방식 제안
- 단계 하나 = 브랜치/PR 하나. 화면 파일은 기능별 폴더(`features/*`)라 팀원이 나눠 작업해도 충돌이 적다.
- 마이그레이션은 `supabase/migrations/`에 새 파일로만 추가하고 기존 파일은 수정하지 않는다.
- 시크릿 키·DB 비밀번호는 저장소에 올리지 않는다(`.env*` 제외됨).
