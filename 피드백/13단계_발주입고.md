# 13단계 피드백 — 발주·입고 (5-1 ~ 5-3)

## 한 일
- 5-1 권장 발주량: `calculate_order_recommendations` 함수가 재료별로 계산해 `order_recommendation`에 저장 (매 계산마다 새 행, 이력 유지)
  - 공식: `예상 소진량 × 보정 계수 − 현재 재고`를 발주 단위(`conversion_rate`)로 올림, 음수면 0
  - 예상 소진량: 가장 최근 마감 기간의 실제 소진량 × (대상 주 예측 매출 ÷ 그 기간 실제 매출, 0.8~1.2로 제한). 예측 매출이 없으면 비율 1, 마감 기록이 없으면 최근 7일 판매 차감량
  - 보정 계수: 대상 기간 시작일에 유효한 가장 최근 `correction_coefficient`
- 5-2 발주 등록: `place_purchase_order` — 발주 단위 배수 검증, 권장량과 다르면 `is_adjusted=true`, 상태 '대기'
- 5-3 입고 처리: `receive_purchase_order` + `receipt` INSERT 트리거 — 상태 '입고완료', 재고 가산, 변동 기록(입고), 부족 해제, 수량 차이는 `diff_qty`·`diff_reason`, 점주에게 알림
- 화면: 권장 발주(다시 계산 버튼, 처음 방문 시 다음 주 기준이 없으면 자동 계산) / 발주·입고 내역 / 입고 처리

## 결정한 것 (이전 제안에서 바뀐 점)
- 이전에 제안한 공식은 안전재고(`min_stock`)를 더하는 형태였으나, **시드 데이터와 화면 문구가 이미 안전재고 없는 공식**이라 그쪽을 따름
- 시드의 권장량(원두 10)과 새 계산 결과(원두 9)가 다른 건 시드는 예측값(14), 새 함수는 직전 실제 소진량(13.3)을 쓰기 때문

## 막힌 부분 🚧
- `sales_forecast`(예측 매출)가 시드에 2026-10-19 주만 있어서 지금은 비율이 1로 계산됨. 1~2단계(매출 예측) 담당자가 다음 주 예측을 만들면 자동 반영됨
- 발주 한 건의 번호(PO-xxxx)는 DB에 헤더 테이블이 없어서 **같은 시각에 등록한 품목 묶음**으로 만들어 표시함 (22개 테이블 확정이라 테이블 추가 안 함)
- 발주를 취소·수정하는 기능은 프로세스 목록에 없어서 만들지 않음
- 거래처(supplier)는 DB에 컬럼이 없어서 화면에 예시 값이 남아 있음 (필요하면 팀 결정 후 컬럼 추가)
- 권한은 개발용 임시(anon이 함수 실행 가능). 인증 후 점주=산출·발주, 매니저=입고로 제한 필요
